# Browser diagnostic and lifecycle acceptance correction

The original `Runtime.evaluate` timeout remains unexplained. The transport still uses the existing 20-second deadline; it does not retry page operations or raise every timeout. It now rejects outstanding requests on socket loss, removes pending timers, handles late responses safely and records bounded request timing plus process/session cleanup. It does not record evaluated expressions or returned page data in transport logs.

The browser runner writes a fresh running record before launch and incomplete failure evidence on either browser startup or evaluation failure. A historical passing report cannot stand in for a failed current run. Six Vitest regressions cover timeout/late reply, connection loss, large resolved replies, send failure and failure-report replacement during startup/evaluation. These tests use the repository's normal Vitest discovery.

The lifecycle soak fails immediately on unexpected pause rather than clicking Resume. Success requires four accepted mock submissions and no practice result or Resume observation. Live/peak scene counts are independent of the bounded trace buffer, so clearing or truncating event history cannot corrupt resource accounting. Final acceptance requires zero live scenes, peak at most one, and the existing resource/listener cleanup invariants.

This tooling is independent of the countdown policy correction. The previous strict soak exposed a zero-tick countdown pause, but its old trace did not retain the triggering frame/lifecycle event. The historical pause, 637 ms stall and CDP timeout remain unresolved limitations; controlled reproduction does not retrospectively prove their causes. All fixtures are local and use synthetic data. No production runtime hooks or settings are introduced.

The renderer recovery fixture also now injects its audio-deadline fault explicitly at audio node preparation. A renderer-only five-second stall could occur after audio readiness had already completed, correctly producing a normal run instead of the recovery UI the test expected. Recovery cases retain the renderer stall and additionally require the `INJECT_AUDIO_WARMUP` marker and an actual degraded audio outcome. The fault runs once per disposable iframe, so Retry and cancellation/stale-result recovery still test a fresh bounded attempt. No assertion accepts an unexpected gameplay pause, and no runtime deadline was raised.

The clock-snapshot instrumentation now checks that a diagnostic object exists before assigning its probe. The standalone responsive fixture intentionally loads the application without that object; the previous injected assignment caused its game error boundary to show “Balance couldn’t load.” This guard is build-time test tooling, not an application-source change.
