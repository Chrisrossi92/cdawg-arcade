5. **Authoritative puzzle model.** Database New York day key selects the puzzle; unique day enforces one publication. The immutable row must exactly match a freshly verified generation certificate and the supported graph/rules snapshot (`chainshift-graph-v2`, `fnv1a64:029bb9393f7bbe48`, `chainshift-rules-v1`). Missing/unpublished, mismatched graph/rules, altered certificates fail closed. Only safe endpoints/identity/day cross the API. Local seeding creates validated `local-candidate` facts without claiming editorial approval or running a scheduler. Daily lookup can recover an owned active old-day attempt even if the new day is unpublished.
6. **Attempt lifecycle.** START authenticates a verified activity session and atomically inserts or returns the same player+puzzle attempt under session/player locks and database uniqueness. Start requires the expected authoritative puzzle ID, so rollover cannot silently claim a different puzzle. GET daily/owned state discovers an active attempt; UI explicitly offers RESUME and reconstructs its route/timer. Renewal, another tab, or another eligible guild cannot create another attempt for that puzzle. No abandonment or timeout resets the entitlement. Completed attempts show official result, practice and comparison, with no second ranked START. An active old-day attempt remains playable and completes against its original puzzle.
7. **Timing and latency.** PostgreSQL `clock_timestamp()` sets claimed time in the INSERT trigger and completion time in the first committed completing UPDATE. Official milliseconds are `floor(extract(epoch from(completed_at-claimed_at))*1000)`; database timestamp precision is finer than exported millisecond ISO strings. All score sorting uses this integer millisecond fact. Client times, routes, final counts and elapsed values are not accepted. Resume supplies a current database elapsed sample, original start, server time and route; the display advances from receipt using local monotonic time and resynchronizes on authoritative responses. Time away, invalid moves and backtracks remain included. Animation/audio occur after server completion. Network transit, server queue/lock waits and referee/database work contribute to official elapsed time; V1 does not claim latency compensation or perfect visual clock synchronization. Known transaction rollbacks may retry; uncertain commits require receipt/state recheck and cannot choose an earlier timestamp. Clock rollback that violates timestamp checks fails closed.
8. **Server referee.** Every accepted ranked edge is validated on the server from its stored current word using the pinned directed referee. Client sends only intended word, revision and request ID. Unsupported inflections, unknown and reversed edges reject without appending. The UI uses confirmed responses rather than permanently optimistic words; temporary request gating prevents overlapping entries and restores focus after confirmation. Local practice still contains the approved graph and allows graph exploration; the graph is not claimed to be a secret.
9. **Backtracking.** Server removes one stored node when above START; START is protected, timer never resets, completed attempts reject mutations. Final shifts derive from the actual completed route length, so removed links do not count. Existing unlock feedback, expanding field, destination anchor, reduced motion and bounded sounds remain. Invalid actions and START no-ops advance revision and receive receipts, making concurrent intent explicit.
10. **Idempotency.** Start uses the player+puzzle unique identity. Shifts/backtracks carry UUID request IDs and expected route revisions; stored digests bind IDs to exact intent. Same-ID retries return confirmed current owned state without reapplying; different payload reuse conflicts. Competing distinct requests at one revision cannot both act. Accepted moves, receipt, and completion commit atomically. Client retains uncertain intent in memory for same-ID retry, or rechecks authoritative state; reload restores the committed attempt rather than replaying arbitrary client routes. No duplicate success effects run for confirmed receipt retries. Bounds: 2KB mutation bodies, 64-character words, 2048 route nodes, 10,000 actions/attempt, request/pending limits, and bounded comparison payloads.
11. **Completion immutability.** The first successful FINISH transaction supplies one completed attempt with database-derived duration and final route. Guards prohibit reopening, route/result changes or deletion, even through ordinary direct table writes; runtime cannot write timing/score columns. Duplicate completion retries preserve the exact timestamp, route, count and duration. Waiting destination/gap disappear immediately on confirmed completion and the existing full-route sweep/sting/result presentation follows. No official result is written to local practice history.
12. **Leaderboard.** Official completed attempts only, shifts ASC then elapsed milliseconds ASC. SQL `rank()` uses only these two score fields: exact ties share rank. Stable player UUID ordering within an exact tie is display order, not a performance advantage; no fabricated podium. Safe display-name conventions and puzzle-scoped pseudonymous player tags are reused. API/UI show up to 100 rows plus the requester's standing even outside that window. Client displays only server-issued official rows. Practice has no path into this table or ranking.
13. **Guild projection.** Global authoritative facts remain player+puzzle. Guild view projects completed results through existing guild participation with membership verified within 30 minutes, using the requester's eligible verified guild. It does not filter by original launch guild or duplicate facts. A player verified in two guilds can appear in both projections from one result. UI can switch global/guild comparison; synthetic cross-guild and membership fixtures pass. Projection membership is intentionally a freshness-based current-context view, not a permanent historical guild roster.
14. **Route privacy.** Every comparison read authenticates verified identity and session. Routes endpoint first requires that same player has completed that exact puzzle. An incomplete requester gets only `routes_locked`; completed requesters may inspect up to 100 completed routes in the authorized global/guild projection. Leaderboard SQL does not fetch route columns; its payload never includes them. Daily payload contains only own route/state plus safe puzzle facts. Expected-player header prevents queued work from crossing an account switch; ownership, CSRF, expiry, revocation, activity origin and verified/eligible guild checks protect reads and mutations. Errors are sanitized codes. No solution certificates/review reports are in either browser bundle. A native comparison dialog handles focus, Escape and focus return.
